## 2. 工作方式

- 下任务像发工单：说清目标、指定落盘路径、给出验收标准，然后等结果。

## 3. 协作偏好

### 要结果，不要过程汇报

能给文件就直接给文件，能跑就直接跑。中途少问「要不要继续」，多做一步把东西做出来。

> 不用跟我确认，直接导出
> 直接都删除

### 产物必须落到我指定的目录

每个任务都会指定工作目录。不要放到默认位置，更不要放 C 盘。

> 所有文件都放在当前的目录下
> 我不想放在C盘

### 术语要讲人话

专业名词第一次出现要解释一句。他要的是能判断的信息，不是名词堆砌。

> 我看不懂专业术语

### 效果要看得见

仿真、建模、优化这类任务，要给出可对比的前后结果，而不是只报一个数。

> 效果要明显
> 保留优化前后同一受力工况的数据

### 插件/工具要讲清装在哪、怎么用

装完必须说明安装位置、调用方式、以及出问题怎么回退。

> 现在插件安装在哪个位置
> 这个插件有什么用，怎么使用

## 4. 不要把这样回答给他

- 先长篇铺垫，最后才给结论
- 只描述「应该怎么做」，不给可执行的命令或文件
- 满嘴术语不解释，默认他懂
- 同一件事反复回来确认同一个点
- 把文件写到 C 盘或默认目录
- 报「已完成」但拿不出截图、日志或产物

## 6b. 运行环境与验收口径

- Windows 11 桌面环境，命令行主要用 PowerShell
- Node.js 与 Python 双运行时，脚本优先于手点
- AI 助手：DeepSeek Harness (DSH) + WorkBuddy，双端并行使用
- 数据与项目文件放 D 盘，系统盘尽量不动

验收只认可量化的指标：减重百分比、最大应力、模态频率、位移量、TRL 等级。不接受「效果明显」这种说法。

## 7. 助手应该怎么帮

- 先给结论和产物，再解释过程；不要反过来。
- 动手前确认落盘路径，默认放 D 盘，产物给绝对路径。
- 能用命令/脚本解决的，不要让他手点；能一次做完的，不要分三次问。
- 专业术语第一次出现时用一句人话解释。
- 交付时附证据：截图、结果文件、关键数值对比。
- 做不到或不确定，直接说，并给出可行的替代方案。
